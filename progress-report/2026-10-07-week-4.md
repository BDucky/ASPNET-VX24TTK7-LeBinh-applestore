## 4. What each piece of work does, and the ASP.NET Core feature behind it

### 4.1 Real email (PR #14, 2026-10-07)

- Registration and password-reset codes go out through Gmail SMTP (MailKit)
  when the settings are present on the machine. Without them, mail is
  written to the log so development needs no mail account.
- ASP.NET Core: options pattern with validation at startup; the Gmail App
  Password is kept in user-secrets, never in the repository.
- Checked for real: a registration code arrived in a Gmail inbox.

### 4.2 Admin area and first admin account (PR #16, 2026-10-07)

- `/Admin` is an ASP.NET Core **Area** behind `[Authorize(Roles = "Admin")]`.
  A visitor is sent to sign in; a customer or employee sees an access-denied
  page with a link back to the store.
- A dashboard counts products, products on sale, customers and orders.
- The first admin is created at startup through Identity's `UserManager`
  from settings in user-secrets, so the same password rule applies. It is
  created once and never promotes an existing customer.
- 26 new tests (138 in total); browser check `verify-admin`: 31 of 31.

### 4.3 Shopping cart, use cases 11-14 (PR #17, 2026-10-07)

- "Add to cart" posts the chosen colour and region. A visitor is asked to
  sign in first and comes back to the same choice (owner's decision).
- Quantities stay between 1 and the stock; sold-out and unpriced choices
  cannot be added; a product taken off sale stays in the cart with the reason
  and leaves the subtotal. The nav shows the item count (a view component).
- Two adds at the same moment end in one line, enforced by unique indexes
  added through an **EF Core migration**. A database failure shows a message,
  not an error page.
- 46 new tests (184 in total); `verify-cart`: 23 of 23.

### 4.4 Checkout and vouchers, use cases 15-16 (PR #18, 2026-10-07)

- The checkout page fills in the saved address, applies a voucher and places
  the order. **Model validation** on the form; anti-forgery on every post.
- Vouchers have their own table (owner's choice), following the report's
  rule: percent or fixed amount, all or some products, a minimum order, a
  usage limit and a time window. Three demo vouchers are seeded.
- Placing runs in one **database transaction**: stock, voucher use and the
  cart change together or not at all. A double submit makes one order; a
  price changed while the page was open is shown again before placing.
- 43 new tests (227 in total); `verify-checkout`: 25 of 25.

### 4.5 Online payment, use case 17 (PR #19, 2026-10-08)

- Checkout offers cash on delivery, VNPay and MoMo. No sandbox accounts were
  available, so VNPay and MoMo go through a gateway page simulated inside the
  app, signed the way VNPay signs (HMAC-SHA512).
- Every attempt is stored. An answer that was changed, has the wrong amount
  or arrives twice cannot mark an order paid or count it twice. "Pay now"
  appears again after a failed or cancelled payment.
- The simulator runs only in the Development environment; the app refuses to
  start with it anywhere else (options pattern, `ValidateOnStart`).
- 46 new tests (273 in total); `verify-payment`: 16 of 16.

### 4.6 Orders after checkout, use cases 18-19, 22-24, 37 (PR #20, 2026-10-08)

- Customers: "My orders", cancel while the order waits for confirmation
  (stock and voucher use come back), email when the order is placed and when
  it ships.
- Anyone can track an order with its number and the receiver's phone; the
  page shows only status and tracking.
- Staff (Admin and Employee roles) list orders by status and confirm, ship
  with carrier and tracking number, complete or cancel. All allowed moves live
  in one rules table; an online order must be paid before it is confirmed.
- Two staff pressing the same button, or a customer cancelling while staff
  confirm, cannot apply a change twice (conditional updates in the database).
- 62 new tests (335 in total); `verify-orders`: 19 of 19.

### 4.7 Admin pages for products, vouchers and accounts, use cases 25-27, 29-31 (PR #21, 2026-10-08)

- Admins add and edit products and variants (price, stock, on sale), choose
  the photo from the shop's own licensed photo library, and take a product
  off sale instead of deleting it, so old orders keep their lines.
- Vouchers: add, edit, delete, with the report's rules; the use count is
  never overwritten, and a used voucher keeps its code.
- Account roles (customer, employee, admin). The person's other sessions end
  at once (Identity security stamp checked on every request).
- Two admins editing the same item, or a sale landing while an admin edits
  stock, cannot overwrite each other (row version check).
- Licensed photos sourced for Mac mini, iPhone Duo and Apple Watch 12, with
  credits on the Photo credits page.
- 63 new tests (398 in total); `verify-admin-catalog`: 15 of 15.

### 4.8 Whole-application review (PR #22, 2026-10-08)

Every page was checked in the browser again, then two reviews covered the
whole code: security and authorization, and correctness under concurrent
requests. Authorization, ownership checks, anti-forgery and payment
signatures came out clean. Seven problems were fixed, each with a failing
test first (see section 6). 410 tests after the fixes.

### 4.9 Sales report, export and invoices, use cases 33-36 (PR #23, 2026-10-08)

- Staff see revenue, paid orders, items sold and average order value for any
  date range, by day and by product. Only paid orders that were not cancelled
  count, grouped by the day in Vietnam time (LINQ aggregation).
- Export to a real Excel file (ClosedXML, three sheets) and a print page the
  browser saves as PDF. Customers and staff print invoices.
- 16 new tests (426 in total); `verify-reports`: 14 of 14, including opening
  the downloaded workbook and printing a real PDF.

### 4.10 Product reviews, use case 32 (PR #24, 2026-10-08)

- A customer can review a product only after an order containing it was
  delivered. One review per customer per product (unique index), editable.
- Product pages show the reviews and the average (a view component). Staff
  reply to and hide reviews; an author's edit never unhides a hidden review.
- 20 new tests (446 in total); `verify-reviews`: 9 of 9.

### 4.11 Compare products, use case 10 (PR #25, 2026-10-09)

- Any visitor, with or without an account, puts up to three products side by
  side: price from, stock, configurations, colours, regions, rating. The list
  is kept in a cookie (owner's decision), so no sign-in is needed.
- The compare page reuses the catalog's own grouping and the review average,
  so it cannot disagree with the product page. A product hidden after it was
  added drops out and frees its place.
- 26 new tests (472 in total); `verify-compare`: 12 of 12.

### 4.12 Filter by price and sort by newest, use case 8 (PR #27, 2026-10-09)

- The product list has price bands: under 10, 10 to 20, 20 to 40, and 40
  million and over. A product shows in a band when one of its configurations
  on sale is priced inside it (owner's choice), and its card shows that price.
- A "Newest" sort, the report's second sort order.
- Every band link keeps the search, category and sort; the search and sort
  forms keep the band. A hand-edited band in the address lists everything.
- ASP.NET Core: query-string model binding into an enum, one table of bands,
  `Url.Action` building the links.
- 20 new tests (492 in total); `verify-catalog-filter`: 16 of 16, comparing
  every band with the database.

### 4.13 Promotions, use case 28 (PR #28, 2026-10-09)

- Admins and employees (the report gives promotions to both) start a
  promotion at `/Admin/Promotions`: a name, percent or fixed amount, a start
  and an end, and all products or some. Code vouchers stay admin-only.
- While it runs, the shop shows and charges the lower price with the old one
  crossed out and the promotion's name, on the product list, the model and
  configuration pages, compare and the cart. The order records the price
  charged. A voucher is then taken from the lower price, and when two
  promotions cover a product the larger discount wins (owner's choices).
  Nothing is ever made free (developer's rule).
- ASP.NET Core and EF Core: a migration adding two columns; one base
  controller with two thin subclasses, each with its own `[Authorize]` role
  list; `TimeProvider`, so a promotion starts and ends without any background
  job; one service that every price goes through.
- 43 new tests (535 in total); `verify-promotions`: 15 of 15, including the
  price written on the placed order in the database.

### 4.14 Batch prices and price history, BM_PRICE_01 (PR #29, 2026-10-09)

- Admins and employees change the price of every variant of chosen products,
  or of a whole category, by a percent (the result rounded to 1.000 dong) or
  by an amount, at `/Admin/Prices` (owner's choices).
- All or nothing: if a price would reach 0, go beyond what the shop stores,
  or someone changes one meanwhile, nothing is changed.
- Every price change, batch or a single save on the product page, is logged:
  old price, new price, how, who and when. The history is on the same page,
  for all products or one.
- ASP.NET Core and EF Core: a migration adding the `PriceChanges` table; one
  database transaction with compare-and-swap writes; `[Authorize]` for two
  roles; model binding that refuses "1.000" typed as an amount.
- 31 new tests (566 in total); `verify-prices`: 11 of 11, every price and
  history row compared with the database.

### 4.16 Photo placeholder and stock intake, use case 20 (PR #32, PR #33, 2026-10-10)

- The five products without a licensed photo show a drawing of their kind
  (watch, tablet, battery) instead of always a phone (owner's choice).
- Admins and employees receive goods at `/Admin/Stock`: supplier, then one
  line per product with quantity and unit cost. The stock goes up in the
  same transaction, and each line keeps the stock before and after
  (BM_STOCK_01). A product twice on one receipt is refused. Receipts print.
- A stock levels page lists every variant, lowest stock first, searchable.
- The browser check found that pressing Back after saving and saving again
  received the goods twice; the form's key now lives in its address, so
  that cannot happen.
- 29 new tests (600 in total); `verify-stock`: 13 of 13.

## 5. How the work was tested

1. **Test first.** Every behavior with a decision in it (a service, a
   controller action that branches, money or stock math) got a failing test
   first, committed as RED, then the code, committed as GREEN. 31 RED commits
   this week.
2. **Real collaborators.** Tests run the real app in memory
   (`WebApplicationFactory`) on a real SQLite database. Only email and the
   database failure cases are replaced.
3. **Concurrency.** Races (two adds, two staff, cancel during confirm, a sale
   during an admin edit) are staged in tests by running the other request's
   SQL at the exact moment it would land.
4. **Mutation checks.** After each GREEN, the key line was broken on purpose
   to prove a test fails. When a test did not catch it, a sharper test was
   added (this happened once this week, on PR #25).
5. **Browser checks.** Each feature has a script under `setup/verify-*/`
   that starts the real app on a fresh database built by the migrations and
   drives Chromium at desktop and phone (390px) width, including error paths.
   All ten were run again on 2026-10-09:

## 6. Problems met and how they were solved

| Problem | Found by | Fix |
|---|---|---|
| Admin forms with a hand-written address had no anti-forgery token (the browser got error 400) | browser check | token added; a new test walks every page and checks each form |
| An admin price typed as shown ("24.990.000") was saved as empty | whole-app review | admin posts check model state and show the error |
| The registration code could be guessed without limit | whole-app review | five wrong codes end the attempt, counted atomically |
| A cancelled order could still be paid online | test for "Pay now" | payment refused; money arriving late is recorded and the order stays cancelled |
| A failed payment attempt was reused by "Pay now" | retry test | the attempt is read untracked after a bulk update |
| Two saves in the same clock tick got the same version | concurrency test | versions now always move forward |
| Settings read in `Program.cs` were not seen by the test host | test | moved to the options pattern |
| On the compare page, the nav count read the old cookie | code review | the count uses the list the page just wrote, capped at 3 |
| The build server reported Razor errors in views nobody changed | build | `dotnet build-server shutdown`, then a clean build; noted in `HANDOFF.md` |
| The cart printed a line of Razor code (`@if ...`) next to the price | browser check | markup on its own lines; a test now checks no code reaches the page |
| A typed code was looked up in every row, promotions included | code review | checkout matches code vouchers only |
| A browser check used the developer's database, which lacked the new columns (error 500) | browser check | the script migrates its copy first; the step is in the handoff |
| "1.000" typed as an amount in a batch was read as 1 dong | web test | amounts must be whole numbers |
| A huge number crashed the prices page or stored a price too big for the column | code review | one price ceiling for every price write |

One process slip: on 2026-10-08 one GREEN commit (`c5d1283`) was made while a
test still failed, because two commands were chained with `;`. It was fixed
in the next commit (`553ae47`); since then commits are made only after the
test run passes.
